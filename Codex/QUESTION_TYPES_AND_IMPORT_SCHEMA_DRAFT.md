# Nous Question Types And Import Schema Draft

This is a draft for user feedback. It is not final.

Purpose:

- Define the question types Nous should support.
- Define the common fields every imported question should have.
- Define a strict structure that external LLMs can output.
- Keep the structure understandable enough that prompts can reliably generate it.

The user should review this and say what feels wrong, missing, too complex, or unnecessary.

## 1. Core Principle

Nous imports a question-bank package generated by an external LLM such as ChatGPT, Gemini, Google AI Studio, or another model.

The LLM must:

- Generate questions only from the provided material.
- Avoid adding outside knowledge unless the prompt explicitly asks for it.
- Make questions difficult enough for real exam preparation.
- Prefer confusing but fair distractors for objective questions.
- Include explanations or source basis so the user can verify why the answer is correct.
- Output a strict machine-readable structure that Nous can parse.

The user can later freely edit all imported questions.

## 2. Package-Level Structure

Recommended top-level package:

```json
{
  "schemaVersion": "nous-question-bank-v1",
  "packageMeta": {
    "title": "Example Topic",
    "description": "Generated from exam material",
    "sourceType": "notes",
    "generatedAt": "2026-06-19T00:00:00.000Z",
    "generator": "external_llm",
    "language": "zh-CN"
  },
  "cards": []
}
```

Notes:

- `schemaVersion` lets Nous know how to parse the package.
- `packageMeta.title` can become the suggested deck/card group name.
- `cards` contains knowledge cards. A card can contain one question or many subquestions.

## 3. Knowledge Card Structure

A knowledge card is the main unit shown in the library/gallery.

```json
{
  "id": "optional_llm_card_id",
  "title": "Card title",
  "summary": "Short summary of the knowledge point",
  "sourceBasis": "Which part of the provided material this card is based on",
  "tags": ["tag1", "tag2"],
  "questions": []
}
```

Recommended meaning:

- `title`: visible card title.
- `summary`: short preview text for gallery cards.
- `sourceBasis`: helps the user verify the LLM did not hallucinate.
- `tags`: topic, chapter, exam point, or concept tags.
- `questions`: one or more questions inside this card.

Simple mode:

- If each card only has one question, `questions` still uses an array with one item.
- This keeps the structure consistent.

## 4. Common Question Fields

Every question should share these fields:

```json
{
  "id": "optional_llm_question_id",
  "type": "single_choice",
  "prompt": "Question text",
  "difficulty": "hard",
  "tags": ["optional"],
  "hint": "Optional hint",
  "explanation": "Why the answer is correct",
  "sourceBasis": "Exact basis from source material",
  "userNote": ""
}
```

Recommended rules:

- `type` determines how Nous renders and checks the question.
- `prompt` is the main question.
- `difficulty` can default to `hard`, but the user does not need manual difficulty controls in the UI yet.
- `hint` is optional. If used during study, Nous may treat the result as `模糊`.
- `explanation` helps with review after revealing the answer.
- `sourceBasis` should cite or summarize the source passage.
- `userNote` is usually empty on import and editable later by the user.

## 5. Objective Question Types

Objective questions have fixed answers. Nous can check them automatically or semi-automatically.

### 5.1 Single Choice

Use when exactly one option is correct.

```json
{
  "type": "single_choice",
  "prompt": "Which statement best matches the material?",
  "options": [
    { "id": "A", "text": "Option A" },
    { "id": "B", "text": "Option B" },
    { "id": "C", "text": "Option C" },
    { "id": "D", "text": "Option D" }
  ],
  "answer": "C",
  "explanation": "C is correct because...",
  "sourceBasis": "Based on..."
}
```

Prompt rule for LLM:

- Distractors must be plausible and highly confusing.
- Avoid obviously wrong options.
- Only one option may be correct.

### 5.2 Multiple Choice

Use when more than one option can be correct.

```json
{
  "type": "multiple_choice",
  "prompt": "Which statements are correct?",
  "options": [
    { "id": "A", "text": "Statement A" },
    { "id": "B", "text": "Statement B" },
    { "id": "C", "text": "Statement C" },
    { "id": "D", "text": "Statement D" }
  ],
  "answers": ["A", "D"],
  "explanation": "A and D are correct because...",
  "sourceBasis": "Based on..."
}
```

Prompt rule for LLM:

- The number of correct options should vary.
- Wrong options should be close to the truth but still clearly wrong according to the material.

### 5.3 True Or False

Use when the user judges one statement.

```json
{
  "type": "true_false",
  "prompt": "This statement is correct: ...",
  "answer": true,
  "explanation": "The statement is true/false because...",
  "sourceBasis": "Based on..."
}
```

Prompt rule for LLM:

- Avoid trivial statements.
- False statements should be subtly wrong, not obviously absurd.

### 5.4 Fill In The Blank

Use when the user must recall a specific word, phrase, number, or concept.

```json
{
  "type": "fill_blank",
  "prompt": "The core concept is ____.",
  "blanks": [
    {
      "id": "blank_1",
      "answers": ["correct answer", "accepted alias"]
    }
  ],
  "explanation": "The blank should be this because...",
  "sourceBasis": "Based on..."
}
```

Prompt rule for LLM:

- The blank should test important knowledge, not random words.
- Accepted aliases should be included when reasonable.

### 5.5 Matching

Use when the user matches terms, concepts, people, causes, effects, definitions, or examples.

```json
{
  "type": "matching",
  "prompt": "Match each concept with the correct explanation.",
  "leftItems": [
    { "id": "L1", "text": "Concept 1" },
    { "id": "L2", "text": "Concept 2" }
  ],
  "rightItems": [
    { "id": "R1", "text": "Explanation 1" },
    { "id": "R2", "text": "Explanation 2" }
  ],
  "pairs": [
    { "left": "L1", "right": "R2" },
    { "left": "L2", "right": "R1" }
  ],
  "explanation": "The matches are correct because...",
  "sourceBasis": "Based on..."
}
```

Prompt rule for LLM:

- Items should be short enough to compare clearly.
- Right-side items can be shuffled by Nous during study.

### 5.6 Ordering

Use when the user must arrange steps, events, causes, or process stages.

```json
{
  "type": "ordering",
  "prompt": "Arrange the following steps in the correct order.",
  "items": [
    { "id": "S1", "text": "First step" },
    { "id": "S2", "text": "Second step" },
    { "id": "S3", "text": "Third step" }
  ],
  "answerOrder": ["S1", "S2", "S3"],
  "explanation": "This is the correct order because...",
  "sourceBasis": "Based on..."
}
```

Prompt rule for LLM:

- Use only when the material has a real sequence.
- Do not force ordering questions when order does not matter.

## 6. Subjective Question Types

Subjective questions are self-judged. Nous should show reference answers and checkpoints.

All subjective questions should include:

```json
{
  "type": "short_answer",
  "prompt": "Question text",
  "referenceAnswer": "A strong answer should say...",
  "checkpoints": [
    "Must include point 1",
    "Must include point 2"
  ],
  "explanation": "How to judge the answer",
  "sourceBasis": "Based on..."
}
```

During study:

- The user answers from memory.
- The answer/checkpoints are hidden first.
- After reveal, the user self-rates: `记住`, `模糊`, or `忘记`.

### 6.1 Short Answer

Use for direct recall in the user's own words.

```json
{
  "type": "short_answer",
  "prompt": "What is the core definition of ...?",
  "referenceAnswer": "...",
  "checkpoints": [
    "Includes the key definition",
    "Mentions the required condition"
  ],
  "sourceBasis": "Based on..."
}
```

Best for:

- Definitions.
- Short concepts.
- Key facts that need phrased recall.

### 6.2 Explanation

Use when the user must explain reason, cause, process, principle, or mechanism.

```json
{
  "type": "explanation",
  "prompt": "Explain why ...",
  "referenceAnswer": "...",
  "checkpoints": [
    "Explains the cause",
    "Explains the process",
    "Connects the result back to the concept"
  ],
  "sourceBasis": "Based on..."
}
```

Best for:

- Why questions.
- How something works.
- Process understanding.
- Cause-and-effect.

### 6.3 Analysis

Use when the user must compare, evaluate, infer, or analyze a scenario/material.

```json
{
  "type": "analysis",
  "prompt": "Analyze the relationship between ...",
  "referenceAnswer": "...",
  "checkpoints": [
    "Identifies the main relationship",
    "Uses evidence from the material",
    "Explains the implication"
  ],
  "sourceBasis": "Based on..."
}
```

Best for:

- Essay-like questions.
- Material analysis.
- Comparison.
- Argument evaluation.
- Higher-order exam questions.

## 7. Cloze And Hidden Text Editing

Cloze can exist in two ways:

1. Imported fill-in-the-blank questions.
2. User-created hidden text inside notes or explanations.

For imported cloze/fill_blank:

- It should be structured so Nous can judge answers.

For user-created hidden text:

- It may be a rich-text editing feature.
- It does not always need automatic grading.
- It can be used for self-testing inside notes.

## 8. Suggested Strict LLM Instructions

The final prompt should include rules like:

- Generate only from the supplied material.
- If the material does not support a question, do not invent it.
- Make questions difficult and exam-oriented.
- For choice questions, make distractors highly plausible.
- Each question must include `sourceBasis`.
- Each objective question must include a fixed answer.
- Each subjective question must include `referenceAnswer` and `checkpoints`.
- Output valid JSON only.
- Do not wrap JSON in Markdown fences unless the user asks for it.
- Do not include comments in JSON.

## 9. Open Questions For User

Questions to clarify next:

1. Should a package contain big knowledge cards with many subquestions, many single-question cards, or both?
2. Do you want `sourceBasis` to contain exact copied source text, a short explanation, or both?
3. For objective questions, should Nous auto-grade immediately or still let the user self-rate memory after seeing the result?
4. Do subjective questions need score levels, or is `记住 / 模糊 / 忘记` enough?
5. Should fill-in-the-blank support multiple blanks in one question?
6. Should matching and ordering be included in the first UI redesign, or just reserved in the schema?
7. Should every question have its own `userNote`, or should notes belong to subquestions only after import?
8. Should imported AI explanations be separate from user notes?

## 10. Confirmed User Decisions From 2026-06-22

These decisions supersede earlier open questions where they conflict.

### 10.1 Card Model

- A card should primarily represent one knowledge point.
- A card may contain many subquestions.
- This is preferred over "one question = one card" as the main model.
- The card should show all relevant content, but most areas should be collapsible.

### 10.2 Review State Scope

- Review should exist at both levels:
  - The whole card has an overall review state/progress.
  - Individual subquestions also have their own review state.
- This allows the UI to show overall card progress while still tracking weak subquestions.

### 10.3 Card Detail Layout

- Card detail should show all content, but everything should be collapsible.
- Left side should have a list/table of subquestions or sections that can be collapsed/hidden.
- The bottom-right should have a compact study/review bar.
- The outer layer of this bar should show the three main choices:
  - 记住
  - 模糊
  - 忘记
- The bar should be expandable/pull-up.
- Expanded bar details should include review metadata such as:
  - Review count.
  - Which review stage this card is currently on.
  - Other detailed review information.

### 10.4 Import Package Scope

- One import package should represent a complete deck generated from the user's current uploaded/provided material.
- The package should include cards covering all content in that material.
- The generation goal is full coverage of the uploaded material, not a small sample.

### 10.5 Source Basis Requirement

- The question bank must be 100% based on the user's provided material.
- Every generated question/card should have a source basis.
- The desired trust model is similar to NotebookLM: the user should be able to see that the answer came from their own material.
- The prompt should explicitly forbid unsupported content and hallucination.

### 10.6 Difficulty

- Future UI may allow selecting difficulty levels.
- For the current prompt/design direction, default to "hell difficulty" or very high difficulty.
- The user wants difficult, exam-oriented questions because LLMs tend to generate questions that are too easy by default.

### 10.7 Objective Question Review Behavior

- For objective questions:
  - If the user answers correctly, allow the user to choose between `记住` and `模糊`.
  - If the user answers incorrectly, treat it as `忘记` automatically.
  - Incorrect questions should enter wrong/redo flow automatically.
- A separate `跳过` option is needed.
- Skipped questions should be practiced again after the normal session, together with wrong questions.
- The desired feel is similar to Duolingo reviewing wrong/skipped items again at the end.

### 10.8 Subjective Question Self-Check

- Do not require checklist-style checkpoint ticking.
- It is too complex because the same concept can be expressed in many ways.
- Core concepts/checkpoints can be shown as reference material only.
- The user should self-judge with `记住 / 模糊 / 忘记`.

### 10.9 Hint Behavior

- If the user uses a hint, the result should count as `模糊`.

### 10.10 Notes

- Notes should appear after the user answers and reveals/checks the answer.
- Notes are for the user's own reflection after seeing the answer.
- AI explanations are reference material and should remain separate from user notes.
- Do not merge AI explanation and user notes by default.

### 10.11 Card Content And Source Presentation

- Every knowledge card must have a title so users can distinguish the topic.
- Every card should have a short summary and core concepts, used together to reinforce memory after answering.
- The subquestion list is needed for quick navigation within a card.
- AI explanation is not a first-stage requirement. Reserve its data field and UI space for a future optional API-assisted feature.
- Source information is lower priority in the visible UI:
  - Keep it compact and collapsed by default.
  - Present it as a small dropdown containing the available source references.
  - Do not make source text dominate the learning surface.

### 10.12 Automatic Card Splitting

- An import package represents one complete deck for the material submitted in that import.
- The external LLM should decide how to split the material into knowledge cards.
- The splitting must still cover all supplied material.
- The preferred rule is: let the LLM identify meaningful knowledge points, rather than forcing one fixed splitting method such as chapter-only or exam-point-only.

### 10.13 Session Repair Loop

- At the end of a study session, wrong and skipped questions enter a repair pool.
- The repair pool repeats until all of its questions are resolved.
- A user may still choose to skip a question during the repair loop; it remains in the pool until resolved or until the user explicitly ends the session.

### 10.14 Multi-Blank Questions

- A fill-in-the-blank question may contain multiple blanks, including three or four blanks in one sentence or passage.
- Each blank must have its own accepted answers and be judged independently.
- The whole question can show partial correctness when some blanks are correct and others are not.

## 11. Remaining Open Questions After 2026-06-22

1. Should every card contain a `cardNote` plus per-question `userNote`, or only per-question notes after answer reveal?
2. What exact source-reference format should the collapsed dropdown use: source name only, section/page name, short excerpt, or a mix?
3. Should matching and ordering be included in the first UI redesign, or reserved in the schema first?
4. When a user explicitly ends a repair loop with unresolved questions, how should those questions be scheduled?
5. Should difficulty levels exist in the import prompt now, even if UI starts with hell difficulty?
